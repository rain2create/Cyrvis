# CYRVIS GUI 加速实验方案（不含 MCP/直连工具）

> 最后更新：2026-11-16
> 范围：只优化 GUI Agent 的「截图 → VLM → 动作 → 等待」循环；本轮**不做** MCP/直连工具。
> 目标：在成功率不明显下降的前提下降低固定任务总耗时；用数据决定是否换 ShowUI-2B。

## 1. 任务谱系与选择原则

上一版 T1–T3 都是「单窗口、文本输入」，对 Action Batching 太友好，不能代表真实任务。v2 按下面 5 个轴取样，避免只用批量友好任务得出偏乐观的结论：

| 轴 | 取值 |
|---|---|
| 窗口/应用 | 单窗口 / 多标签 / 跨应用 |
| 状态依赖 | 低（输入后回车）/ 中（表单）/ 高（搜索结果、日期选择、对话框） |
| 页面类型 | 桌面应用 / 本地网页 / 真实网站 / 系统设置 |
| 任务长度 | 短（2–4 轮）/ 中（5–10 轮）/ 长（10+ 轮） |
| 批量友好度 | 高 / 中 / 低 |

### 任务矩阵

| ID | 场景 | 窗口/应用 | 长度 | 状态依赖 | 批量友好 | 主要测什么 |
|---|---|---|---|---|---|---|
| L1 | 记事本输入 + 保存 | 单窗口 / Notepad | 短 | 低 | 高 | 批量上界、输入+回车+保存 |
| L2 | 计算器 12 + 34 | 单窗口 / Calculator | 中 | 中 | 中高 | 视觉定位、连续点击 |
| L3 | 本地表单填写 | 单窗口 / Chrome | 中 | 中 | 中 | 多字段、click+type、提交 |
| L4 | 本地搜索 → 新标签 → 详情 | 多标签 / Chrome | 中长 | 高 | 低 | 动态结果、标签切换、读信息 |
| L5 | 跨应用读码 → 记事本保存 | 跨应用 / Chrome+Notepad | 中长 | 高 | 低 | 窗口切换、记忆、保存 |
| L6 | 另存为对话框 | 单应用 + 对话框 | 中 | 高 | 低 | 应用启动、对话框、路径输入 |
| L7 | Windows 设置读取版本号 | 单窗口 / Settings | 中 | 中 | 低 | 嵌套导航、密集 UI |
| R1 | 携程查上海→巴黎机票 | 真实网站 / Chrome | 长 | 高 | 低 | 真实网站、日期选择、结果读取 |
| R2 | 搜索并提取信息 | 真实网站 / Chrome | 中长 | 高 | 低 | 搜索、结果筛选、信息提取 |
| R3 | 真实网站 + 记事本 | 跨应用 / Chrome+Notepad | 中长 | 高 | 低 | 真实信息 + 跨应用写入 |

**第一批只跑 4 个：L1、L4、L5、R1。**  
每个任务代表一类，已经能覆盖“批量友好 / 状态依赖 / 跨窗口 / 真实长任务”四个维度；L2、L3、L6、L7、R2、R3 进候选池，不在第一批跑。

| 组 | 任务 | 作用 |
|---|---|---|
| 批量友好 | L1 记事本输入+保存 | 看 Action Batching 的加速上界 |
| 状态依赖 | L4 本地搜索 → 新标签 → 详情 | 动态结果，不能盲批量 |
| 跨窗口 | L5 跨应用读码 → 记事本保存 | 应用启动、窗口切换、记忆 |
| 真实长任务 | R1 携程上海 → 巴黎机票 | 真实网站、长链路、泛化 |

这样每轮配置只需要跑 **4 个任务 × 1 次**（方向性基线；波动大时再补跑），不会把时间耗在重复场景上。

## 2. 受控任务（本地，确定性判据，用于 A/B）

### 环境基线

| 项 | 值 |
|---|---|
| OS | Windows 11 Pro，单屏 2560×1440，125% 缩放 |
| App | CYRVIS / UI-TARS Desktop，记录 commit |
| VLM | `doubao-seed-2.1-lite`，Ark Plan 接口 |
| Prompt | `getSystemPromptDoubao_15_15B`（含 Action Batching） |
| loopIntervalInMs | 1000（基线） |
| 历史截图 | 5 张（基线） |
| 截图像素上限 | Doubao 4.0MP（基线） |
| 干扰控制 | 关闭通知/微信/QQ，固定窗口位置，专用 Chrome profile |

### L1：记事本输入 + 保存（批量上界）

| 项 | 内容 |
|---|---|
| 初始状态 | `D:\temp\cyrvis-bench\l1-notepad.txt` 内容为 `PRE `，Notepad 打开该文件，光标在末尾，窗口固定 |
| 指令 | 「在当前记事本文档末尾输入 batch test，然后按回车，并保存文件。」 |
| 成功判据 | 文件内容为 `PRE batch test\n` |
| 注意 | 文件已存在，Ctrl+S 直接保存，不弹 Save As |

### L2：计算器（视觉定位 + 连续点击）

| 项 | 内容 |
|---|---|
| 初始状态 | 新开 Windows 计算器，显示 0，窗口固定 |
| 指令 | 「只用鼠标点击计算器按钮，计算 12 + 34，确认结果显示 46。」 |
| 成功判据 | 计算器显示 46；日志中至少 4 个 `click` 动作 |
| 注意 | 若模型改用键盘，记为「未按指令点击」，单独统计；总时间仍记录 |

### L3：本地表单页（同页多字段 + 提交）

| 项 | 内容 |
|---|---|
| 初始状态 | 本地 `http://127.0.0.1:8765/form.html`，Chrome app 窗口（专用 profile，固定 1200×900） |
| 表单 | Name、Email 两个输入框 + Submit 按钮；提交后显示 `Submitted` |
| 指令 | 「在浏览器当前页面中，姓名填写 CYRVIS，邮箱填写 test@example.com，然后点击 Submit，确认页面显示 Submitted。」 |
| 成功判据 | 本地服务收到 `{"name":"CYRVIS","email":"test@example.com"}` 的 POST |
| 注意 | 成功判据走服务端日志，不依赖模型自述 |

### L4：本地搜索 → 新标签 → 详情（状态依赖）

| 项 | 内容 |
|---|---|
| 初始状态 | 本地站点 `http://127.0.0.1:8765/search.html`，10 条结果，第 3 条进入 `/detail/3` |
| 指令 | 「在本地测试网站搜索 PARIS，在新标签页打开第 3 个结果，读出详情页的取件码并告诉我。」 |
| 成功判据 | 服务端访问日志包含 `/search?q=PARIS` 和 `/detail/3`；`finished(content=...)` 包含详情页的取件码 |
| 测什么 | 动态结果选择、标签切换、读信息、不能靠盲批量 |
| 注意 | 详情页的取件码每轮随机生成并由服务端记录，防止模型猜中 |

### L5：跨应用读码 → 记事本保存（跨窗口）

| 项 | 内容 |
|---|---|
| 初始状态 | 只打开 Chrome 的 `/code` 页面，显示 6 位取件码；Notepad 关闭 |
| 指令 | 「读取浏览器页面上的取件码，打开记事本，把取件码写进去，并保存到 `D:\temp\cyrvis-bench\code.txt`。」 |
| 成功判据 | 文件内容包含服务端生成的 6 位取件码 |
| 测什么 | 应用启动、窗口切换、读后记忆、写入、保存 |
| 注意 | 每轮重置取件码；启动前删除目标文件 |

### L6：另存为对话框（对话框/导航）

| 项 | 内容 |
|---|---|
| 初始状态 | 新开无标题 Notepad，目标文件不存在 |
| 指令 | 「打开记事本，输入 CYRVIS save test，然后另存为 `D:\temp\cyrvis-bench\l6-save-as.txt`。」 |
| 成功判据 | 文件存在且内容包含 `CYRVIS save test` |
| 测什么 | 应用启动、Save As 对话框、路径输入 |
| 注意 | 波动大，作为 Tier 2；前五个稳定后再加 |

### L7：Windows 设置读取版本号（嵌套导航）

| 项 | 内容 |
|---|---|
| 初始状态 | Settings 关闭；系统版本号由注册表预取 |
| 指令 | 「打开 Windows 设置，进入系统 → 关于，读出 Windows 版本号。」 |
| 成功判据 | `finished(content=...)` 包含注册表中的版本号/OS build |
| 测什么 | 应用启动、嵌套导航、密集 UI、读信息 |
| 注意 | 不修改任何设置，只读取 |

## 3. 真实任务（验证泛化，不作为严格 A/B）

真实网站有网络、动态内容、Cookie、反爬和验证码，不能像本地任务一样稳定复现。这里只做**定性/半定量验证**：记录成功、总时长、卡点；环境失败（验证码/网络）单独标记，不算模型失败。

### R1：携程查上海 → 巴黎机票（长任务）

| 项 | 内容 |
|---|---|
| 指令 | 「打开携程官网，查询 30 天后上海到巴黎的单程机票；只查看结果页第一个航班的价格和航班号，不要登录、不要预订、不要填写任何乘客信息。」 |
| 成功判据 | `finished(content=...)` 或最终截图包含第一个航班的价格/航班号；人工或 LLM 判定 |
| 测什么 | 真实网站、城市选择、日期选择、结果页读取、长链路恢复 |
| 安全 | **只查询，不预订、不登录、不填写个人信息**；出现登录/支付/乘客信息页面立即停止 |
| 风险 | Cookie 弹窗、验证码、反爬、页面改版；记为环境失败 |

### R2：搜索并提取信息

| 项 | 内容 |
|---|---|
| 指令 | 「用百度搜索 UI-TARS 2.0 的发布时间，打开一个可信来源，读出日期。」 |
| 成功判据 | 最终回答包含日期；人工/LLM 判定 |
| 测什么 | 搜索、广告/结果筛选、信息提取 |
| 风险 | 搜索结果动态、广告、验证码 |

### R3：真实网站 + 跨应用

| 项 | 内容 |
|---|---|
| 指令 | 「打开中国天气网，查询北京今天最高气温，打开记事本写入并保存到 `D:\temp\cyrvis-bench\weather.txt`。」 |
| 成功判据 | 文件包含温度；与页面读数一致 |
| 测什么 | 真实信息读取 + 跨应用写入 |
| 风险 | 页面动态、网络 |

## 4. 指标

| 指标 | 采集方式 |
|---|---|
| 成功率 | 每个任务的独立判据（文件/服务端/UIA/人工判定），3–5 次取比例 |
| 墙钟耗时 | `runAgent` 开始到 `[GUIAgent] Finally` 的时间戳 |
| 轮数 | `[GUIAgent] >>> totalTokens ... loopCnt: N` |
| 模型调用次数 | 日志中 `[GUIAgent] consumes` 条数 |
| 批量大小 | `[GUIAgent] action batch { count, types }` |
| Token | `costTokens` 累加；prompt/completion 分开记录 |
| 分阶段耗时 | 截图、VLM `costTime`、动作执行、sleep |
| 指令遵守 | L2 是否只用鼠标、L4 是否新标签、R1 是否未登录/未预订 |
| 失败类型 | 解析失败、误点、超时、max loop、模型误报完成、环境失败 |
| 成本 | token × 单价（可选） |

按用户决定，第一阶段每项配置每个任务只跑 **1 次**，作为方向性基线；不取中位数、不做统计显著性。  
如果某个配置明显有效或异常，再补跑 2–3 次确认。真实任务每配置先跑 **1 次**，只做成功率/卡点记录，不和本地任务混在一起算平均。

### 按类别汇报

不要把 L1 的成绩当成整体结论。报告至少分四组：

| 组 | 第一批任务 | 候选池 | 预期 |
|---|---|---|---|
| 批量友好 | L1 | L2、L3 | Action Batching 收益最大 |
| 状态依赖 | L4 | - | 批量收益小，主要看模型延迟/轮数 |
| 跨窗口 | L5 | L6、L7 | 批量收益小，主要看规划/切换 |
| 真实长任务 | R1 | R2、R3 | 看成功率、卡点、恢复能力 |

## 5. 加速变量

| ID | 变量 | 基线 | 实验 | 需要改代码 |
|---|---|---|---|---|
| B0 | 基线 | 当前配置 | - | 否 |
| E1 | 轮间等待 | 1000ms | 300ms | 否（settings） |
| E2 | 历史截图 | 5 张 | 1 张 | 小改：`maxImageLength` 可配置 |
| E3 | 截图像素上限 | 4.0MP | 2MP | 小改：`maxPixels` 可配置 |
| E4 | Thought 长度 | 当前 | 「Thought ≤ 20 词」或只输出 Action | 否（prompt 变体） |
| E5 | 组合 | - | E1+E2+E3（各自有效时） | 小改 |
| E6 | 模型 | Seed 2.1 Lite | ShowUI-2B 适配层 | 是（Python 服务） |
| E7 | 提前结束 | 每任务最后再问一次 finished | 已知终态时跳过最后一轮 | 是（Controller/任务语义） |
| E8 | 上下文复用 | 全量重发 | Responses API / previous_response_id | 是（需验证 Ark 支持） |

优先做 E1–E4（零/低成本），再做 E6。E7/E8 作为后续增强。

**接受标准**：E1–E4 必须在 L1/L4/L5 三个受控任务上测试；如果只在 L1 变快、在 L4/L5 掉成功率，则不采纳。R1 只跑基线 B0 和最终组合 E5，不参与每个单变量实验。最终按「成功率优先、墙钟其次」排序。

## 6. 实验顺序

1. **P0 基线**：搭好 L1/L4/L5 + R1，跑 B0，确认判据稳定、日志可解析。
2. **P1 零成本调参**：E1 → E2 → E3 → E4，在 L1/L4/L5 上单变量对比；有效的组合成 E5。
3. **P2 小模型**：ShowUI-2B 适配层，先跑 L1/L4/L5，再考虑 R1；与 B0/E5 对比。
4. **P3 决策**：按分组成功率与墙钟选默认配置，写 `doc/benchmark-results.md`。

每阶段结束更新 `doc/progress.md` 与 `doc/findings.md`；不直接改生产默认值，先出数据。

## 7. Benchmark Harness

建议目录：

```text
scripts/cyrvis/bench/
  fixtures/
    form.html          # L3
    search.html        # L4
    detail.html        # L4
    code.html          # L5
    server.js          # 8765；记录 /submit、/search、/detail/:id、/code
  setup.ps1            # 文件、窗口位置、Chrome、Notepad、Calculator、Settings
  run-task.js          # CDP setInstructions + runAgent
  collect.js           # 解析日志，输出 CSV/JSON
  run-suite.js         # 配置 × 任务 × 次数 编排
  results/
```

要点：

- App 用 `pnpm --filter ui-tars-desktop debug` 启动（9222 端口）。
- 配置切换：改 electron-store 的 `loopIntervalInMs`、`maxImageLength`、`maxPixels`、模型字段；每次重启 app。
- **焦点守卫**：每 500ms 检查前台窗口标题；不是目标任务窗口（含允许的对话框）就 `stopRun` 并记失败，防止输入打到个人窗口。
- L3/L4/L5 用独立 Chrome profile + 固定窗口；L4 的结果链接 `target="_blank"`，强制新标签。
- L5 启动时只开 Chrome；Notepad 由模型自己打开，测试跨应用。
- 成功判据独立于模型：文件内容、本地服务日志、Windows UIA、注册表。
- 真实任务 R1–R3 使用独立 Chrome profile，出现登录/支付/验证码立即停止并记环境失败。
- 所有产物放 `D:\temp\cyrvis-bench\`，不进仓库。

## 8. ShowUI-2B 适配层

### 服务

| 项 | 方案 |
|---|---|
| 模型 | `showlab/ShowUI-2B`（Qwen2-VL-2B，MIT） |
| 显存 | BF16 约 5.1GB；4-bit 约 2–3GB，5060 8GB 可跑 |
| 部署 | Python + PyTorch CUDA 12.8+（5060 是 Blackwell）+ Transformers + FastAPI |
| 接口 | OpenAI 兼容 `POST /v1/chat/completions`（非流式） |
| 输入 | UI-TARS 的 messages：文本 + 截图 base64 |
| 输出 | 把 ShowUI 的 dict 动作转成 UI-TARS 的 `Action:` 文本 |

### 动作映射

| ShowUI | UI-TARS |
|---|---|
| `CLICK` + `[x,y]`（0–1） | `click(start_box='[x*1000,y*1000,x*1000,y*1000]')` |
| `INPUT` + `value` + `position` | `click(...)` + 空行 + `type(content='...')` |
| `ENTER` | `hotkey(key='enter')` |
| `SCROLL` + position | `scroll(start_box='[...]', direction='down/up')` |
| `ANSWER` + value | `finished(content='...')` |
| 多个 dict | 用空行连接成多个动作 |

### 主要风险

1. ShowUI 没有 `finished`，需要定义完成判定；先用 `ANSWER` + 任务语义补。
2. ShowUI 训练数据偏 Web/英文；中文指令和 Windows 桌面应用要实测。
3. Blackwell + Windows 的 PyTorch/量化兼容性要最先验证。
4. 2B 模型可能多轮误点；必须用成功率而不是单次延迟判断。
5. Hugging Face 直连可能不通；准备 ModelScope/hf-mirror 备选。
6. L4/L5 这类状态依赖/跨窗口任务，最可能暴露 2B 模型的规划短板；如果 L1 快但 L4/L5 崩，就不能作为默认。

## 9. 需要确认

1. 第一批 4 个任务（L1/L4/L5/R1）是否认可；L2/L3/L6/L7/R2/R3 后续需要时再加。
2. 真实任务（R1 携程）是否允许跑：只查询、不登录、不预订、不填写个人信息；出现验证码/登录即停止。
3. Benchmark 在你桌面空闲时跑，还是用独立 Windows 账户/VM（更安全但更重）。
4. 是否现在下载 ShowUI-2B（约 5GB）并装 Python/PyTorch 环境。
5. 是否允许为 E2/E3 增加两个可配置项（`maxImageLength`、`maxPixels`）。

## 10. 不在本轮范围

- MCP / 直连工具（用户明确先不做）。
- 语音链路、UI、眼动、主动性。
- 生产默认值切换；本轮只产出 benchmark 数据和候选配置。
- 真实网站的登录、预订、支付、个人信息填写。
